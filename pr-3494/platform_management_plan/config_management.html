PF Configuration Management Plan#

Purpose#

The Configuration Management Plan defines how the integrity, consistency, and traceability of project-relevant work products and other configuration items are established and maintained throughout the project lifecycle.

Objectives and scope#

The objective of this plan is to define:

  • how configuration items are identified;

  • where configuration items are stored;

  • how configuration items are made available to relevant stakeholders;

  • how configuration items can be located;

  • how specific versions of configuration items can be retrieved;

  • how modifications to configuration items are controlled;

  • how versions of configuration items are created and stored;

  • how baselines are established and managed;

  • how backup, recovery, and long-term storage are handled; and

  • how configuration status is monitored and reported.

For the definition of Configuration Item, see doc_concept__configuration_process.

Approach#

Configuration management in S-CORE covers the identification, storage, retrieval, modification control, versioning, branching, and baselining of configuration items, as well as backup, recovery, and configuration status reporting.

Lifecycle#

Configuration management applies throughout the complete S-CORE development lifecycle, including the Concept, Development, and Maintenance phases.

Configuration items remain subject to configuration management for as long as they are maintained or required as project evidence.

Identification and Properties#

Each work product is identified by its Sphinx-Needs ID. This also applies to documents, which are identified through their document header as defined in gd_temp__documentation.

The complete list of project documents is maintained in PF Documentation Management... (doc__platform_documentation_mgt_plan).

Sphinx-Needs IDs are checked for uniqueness according to gd_req__configuration_uid. Sphinx-Needs is also used to maintain the properties and attributes of work products as defined by the applicable process area descriptions.

Work products are stored in text or source-code files within GitHub repositories. Files are identified by their repository-relative path and filename.

GitHub repositories realize the Delivery Containers described in doc_concept__general_building_blocks. S-CORE consists of the platform repository and additional repositories containing sets of Dependable Elements for which a rl__delivery_team is responsible.

Each S-CORE repository shall contain a single MODULE.bazel file defining its version and dependencies. Additional MODULE.bazel files are permitted only where required for testing purposes.

Other configuration items are identified as follows:

  • Files: identified by their repository-relative path and filename and maintained under version control in GitHub.

  • Precompiled tools and binaries: identified by the Bazel build configuration, including integrity information such as a hash, where applicable.

  • External tools and binaries built by the S-CORE CI: identified by the version defined in the Bazel build configuration.

Retrieval#

Work products and files are stored in GitHub repositories and can be retrieved in accordance with the applicable Eclipse Foundation access and contribution rules.

The applicable work products are defined by the corresponding process and process-area work-product descriptions. Their locations within the project structure can be determined using Platform Folder Structure.

Git provides access to version-controlled states of a file. In GitHub, the History view can be used to inspect the commits affecting a file, while the Blame view provides line-level information about the commits in which content was introduced or modified.

Baselines can be retrieved through Git tags. A tag identifies a defined repository state associated with a specific baseline and is used as the basis for producing release artifacts such as documentation, software, and verification reports.

Release versioning follows the rules defined in the applicable release guidelines and in Release Management Plan (doc__platform_release_management_plan).

External artifacts required by S-CORE shall be integrated using a controlled and reproducible mechanism. Their source, version, and, where applicable, integrity information shall be recorded in the corresponding build configuration.

Control and Modification#

New work products and modifications to existing configuration items are prepared by a rl__contributor on a development branch.

Changes are submitted through GitHub Pull Requests for review and integration into the main branch. After successful review and fulfillment of the applicable merge criteria, the change is merged by a rl__committer.

The Pull Request records the proposed modifications and provides the primary basis for review and approval of the implementation.

Changes subject to formal Change Management shall additionally follow the process defined in PF Change Management Plan (doc__platform_change_management_plan). The associated Change Request and Pull Requests provide traceability between the requested change and the modified configuration items.

Changes to tools and binary dependencies, including version updates, are controlled through the Bazel build configuration. These configuration files are themselves version-controlled and subject to the same GitHub-based change and review process.

Branches and Baselines#

Branches support parallel and controlled development. S-CORE uses the following branch types:

  • Development branches: created from a remote branch and used by Contributors to prepare changes. No project-wide naming convention is imposed unless otherwise specified.

  • Main branch: the remote main branch containing the latest integrated changes that have passed the applicable CI checks and review process.

  • :term:`Release Branch`: a remote branch derived from main and used to prepare a release. Functional development is not permitted on a release branch; changes are restricted to bug fixes and improvements resulting from verification activities. Merges into a release branch require approval by a rl__project_lead. Release branch naming follows doc_concept__rel_process.

A remote branch resides in the GitHub repository and is distinguished from a developer’s local branches.

S-CORE configuration items maintained in GitHub are baselined at repository level. A repository baseline identifies a consistent state of the configuration items contained in that repository.

Baselines are established using Git tags. The tag name shall follow the release versioning scheme and identify the applicable release, patch version, and, where applicable, pre-release version.

For further information, see Release Management Plan (doc__platform_release_management_plan).

As described in Identification and Properties, S-CORE consists of multiple repositories. Baselines are therefore established individually for each repository. Repositories may use different versioning schemes where appropriate.

Where repositories depend on one another, the providing repository shall be baselined before the consuming repository. The consuming repository records the version or baseline of its dependencies. Consequently, a platform baseline also identifies the versions of the Delivery Containers from which the platform is composed. These versions are also reported in the platform release notes.

Changes made on a release branch that are also applicable to continued development shall be incorporated into main. The responsible Delivery Team defines the appropriate mechanism, for example by implementing the change on main and cherry-picking it to the release branch, or by propagating an approved release-branch change back to main.

Backup and Recovery#

The primary project repositories are hosted using infrastructure provided by the Eclipse Foundation.

Repository availability, backup, and recovery are supported by the applicable Eclipse Foundation hosting infrastructure and services.

Additional measures for long-term retention of configuration items are defined in gd_req__config_workproducts_storage.

Status and Reporting#

Work products defined by the S-CORE processes have status attributes that are used to communicate their maturity and configuration status to stakeholders.

The primary overview for documents is the project document list, which contains the planned documents and their current status. The document list is maintained in the Documentation Management Plan PF Documentation Management... (doc__platform_documentation_mgt_plan), which is part of the Platform Management Plan as defined in gd_guidl__documentation.

At least for every release, the completeness of the applicable configuration baseline is checked against the list of planned documents maintained in the Documentation Management Plan.

Work products that consist of multiple Sphinx-Needs elements are collected into a corresponding document. For example, a feature requirements document (doc__*) contains the associated feature requirements (feat_req__*). The same principle applies to requirements, architecture, detailed design, and safety analysis work products.

Source-code and test-code files are not represented as documents in this sense. Their controlled state is established through version control and the applicable review, verification, and CI checks required before integration.

The configuration status and versions of applicable tools are reported through a tool list. The tool list may be maintained within the Documentation Management Plan or referenced from it and shall also be subject to completeness checks.

Configuration Management Tooling#

S-CORE implements configuration management primarily through the standard version-control infrastructure provided by the Eclipse Foundation together with the project’s Docs-as-Code and build infrastructure.

The principal configuration management tools are:

  • Version control and collaboration: Git and GitHub

  • Docs-as-Code and work-product identification: Sphinx-Needs

  • Build and dependency management: Bazel

Git and GitHub provide storage, versioning, retrieval, modification control, branching, change history, and baselining of configuration items.

Sphinx-Needs provides identification, attributes, relationships, and traceability for work products represented within the project documentation.

Bazel provides reproducible build and dependency configuration and identifies the versions of tools, binaries, and repository dependencies used to produce S-CORE artifacts.

Together, these tools support the configuration identification, control, traceability, retrieval, baselining, and status-reporting mechanisms defined by this plan.
