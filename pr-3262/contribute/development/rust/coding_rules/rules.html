SCR-RUST-001: Define the supported Rust language and build configuration#

Rule (Required). Pin the toolchain, edition, target, features, panic strategy and overflow settings for every production build, and record which language specification the toolchain follows.

Why it matters in Rust. Rust has no single frozen language standard. What a program means depends on the compiler release, the edition and the build settings. A behaviour verified on one configuration is not verified on another, and an unstable feature can change under you.

Requirement. Each component shall record its compiler/toolchain revision, the language specification revision used as the reference for that toolchain (for example a Ferrocene Language Specification revision, with relevant known differences noted), Rust edition, target, dependency resolution, enabled features, panic strategy and overflow-check settings. Production builds shall use this controlled configuration. Stable toolchains reject unstable features; where a nightly or custom toolchain is permitted, the assessment shall list the permitted unstable features and the assumptions relied on. Links to the existing configuration and assessment records satisfy this requirement.

Check. Check manifests, lockfiles and Bazel toolchain/configuration in CI; review language and target assumptions against the referenced specification and the compiler documentation.

Sources, level and coverage limits

Scope: All production crates and their build inputs.

Origin: S-CORE interpretation of MISRA C++:2023 guidelines.

MISRA C++:2023 sources (draft SCRC assessment): 4.1.1 (SCRC draft: safe).

Coverage limit: A successful build does not establish tool qualification. Reconcile Cargo and Bazel inputs; a host-only build does not cover QNX or a different feature set.

SCR-RUST-002: Enforce selected diagnostics and control suppressions#

Rule (Required). Turn the agreed unused-code, unreachable-code and deprecated-API warnings into errors, and make every suppression name its reason.

Why it matters in Rust. Warnings are only enforcement if the build fails on them. A warning that is allowed away, or that never reaches the Bazel action, provides no evidence. Dead and unreachable code hides logic errors and makes review harder.

Requirement. The adopted lint profile shall make selected unused-code, unused-value, unreachable-code and deprecated-API diagnostics blocking. Any suppression shall identify a scoped rationale and rule/deviation. Suppressions inherited from generated or third-party code shall be recorded separately.

Check. Candidate rustc lints: dead_code, unused_variables, unused_assignments, unreachable_code, unused_must_use and deprecated. Verify flags actually reach every Bazel and Cargo analysis action.

Sources, level and coverage limits

Scope: All first-party production crates.

Origin: S-CORE interpretation of MISRA C++:2023 guidelines.

MISRA C++:2023 sources (draft SCRC assessment): 0.0.1 (SCRC draft: safe), 0.2.1 (SCRC draft: safe), 0.2.2 (SCRC draft: safe), 0.2.3 (SCRC draft: safe), 0.2.4 (SCRC draft: safe), 4.1.2 (SCRC draft: safe).

Coverage limit: Warnings are not hard language guarantees. These diagnostics are partial, especially for semantic unreachability, public APIs and feature-disabled code. Do not equate a warning-free build with complete coverage of the mapped rules.

SCR-RUST-003: Avoid invariant decisions and ineffective writes#

Rule (Required). Do not write conditions whose outcome cannot change at runtime, and do not write values that are overwritten or dropped before anyone reads them.

Why it matters in Rust. A fixed condition means one branch is dead and the decision it pretends to make does not exist. An overwritten write usually means a forgotten use or a wrong variable. In Rust, replacing an owning value also runs its destructor, so the write can have an effect you did not intend.

Requirement. A condition shall express a decision whose outcome can differ at runtime for inputs the component accepts. A condition whose outcome is fixed is a violation, whether it is a constant expression or fixed by construction, such as testing a value just assigned from a literal or comparing an integer with itself (floating-point self-comparison is not fixed, since x == x is false for NaN). Designated configuration choices (a cfg predicate or a named constant flag) and intentional loops with an explicit exit are permitted. A value shall not be written and then overwritten or dropped before any observation; this covers assignments overwritten before being read and owning values replaced before being observed. Replacing an owning value runs its Drop, so such a write is unnecessary only when neither the value nor its destructor effect is required.

Example.

const MAX_FRAME: usize = 1024;

// Compliant: the outcome depends on runtime input.
fn accept(frame: &[u8]) -> Result<(), ()> {
    if frame.len() > MAX_FRAME { return Err(()); }
    Ok(())
}

// Non-compliant: the condition is fixed by construction.
fn accept(frame: &[u8]) -> Result<(), ()> {
    let ready = true;
    if ready { return Ok(()); }
    Err(())
}

Both compile. The first decides on the accepted input; the second always takes the first branch, so the else path is dead and the decision is meaningless unless ready is a documented configuration flag.

Check. rustc unused_assignments; selected Clippy condition/comparison checks; candidate CodeQL control-flow and value-use analysis; review intentional constant branches.

Sources, level and coverage limits

Scope: Production control flow.

Origin: S-CORE interpretation of MISRA C++:2023 guidelines.

MISRA C++:2023 sources (draft SCRC assessment): 0.0.2 (SCRC draft: safe), 0.1.1 (SCRC draft: safe).

Adaptation notes: Adapts 0.0.2 (invariant controlling expressions) and 0.1.1 (dead writes). The object scope is widened from trivially destructible C++ objects to all Rust values, since replacing an owning value runs Drop.

Level rationale: Required although both sources are Advisory: an invariant condition or an ineffective write usually indicates a logic defect, the consequence in Rust is the same as in C++, and compiler and Clippy checks make conformance cheap to demonstrate.

Coverage limit: Local diagnostics do not establish path feasibility or detect every overwritten value across calls, and unused_assignments does not consider destructor effects. Record intentional loop and configuration exceptions.

SCR-RUST-004: Handle results and preserve error information#

Rule (Required). Use every non-unit result or discard it deliberately with a visible reason, and never silently throw away an error the API says you must act on.

Why it matters in Rust. Result makes errors visible, but let _ =, .ok() and a catch-all arm make them invisible again. #[must_use] only tells you a value was ignored. Whether ignoring is acceptable depends on what the API’s error contract says.

Requirement. Non-unit results of explicit function and method calls shall be used or deliberately discarded under the project’s reviewed discard convention, for example a let _ = binding with a comment naming why the value is not needed. #[must_use] contracts apply in addition, including to functions returning unit. Errors shall be propagated, converted with necessary context, or handled according to the API’s documented error-handling contract. A Result is critical when that contract states that the error requires action by the caller; discarding a critical error through let _, drop, .ok(), a default value or a catch-all branch is prohibited unless the branch implements the documented recovery. Project APIs shall carry #[must_use] where omission is a defect and shall document which errors require action and what handling is acceptable.

Check. rustc unused_must_use and selectively unused_results; Clippy let_underscore_must_use; candidate CodeQL checks for project error-discard patterns; review recovery paths.

Sources, level and coverage limits

Scope: Production APIs and their callers.

Origin: S-CORE interpretation of MISRA C++:2023 guidelines.

MISRA C++:2023 sources (draft SCRC assessment): 0.1.2 (SCRC draft: safe).

Adaptation notes: Adapts 0.1.2, which covers explicit function-call syntax and excludes operator syntax; an explicit let _ = with a reason is the Rust analogue of the void cast counting as use.

Coverage limit: #[must_use] checks that a result is used, not that it is handled meaningfully. Whether .ok() or a catch-all branch discards or recovers rests on the API contract, which no lint can judge; broad unused_results can flag intentional side-effect APIs.

SCR-RUST-005: Define floating-point range and precision contracts#

Rule (Required). Write down the numerical contract for safety-relevant floating-point code: range, precision, rounding, tolerance, NaN and infinity handling, and what serialization preserves.

Why it matters in Rust. Floating-point arithmetic is approximate and f64 cannot represent every integer or decimal exactly. Without a stated contract there is no way to test whether a comparison tolerance or a stored value is correct, and the error is silent.

Requirement. Safety-relevant floating-point calculations shall be covered by a numerical contract that specifies acceptable range, precision, rounding, comparison tolerance, handling of NaN, infinity and signed zero, and serialization guarantees. One shared contract may cover all calculations it applies to, for example at a module or API boundary, provided each calculation is traceable to it. Serialization shall preserve the required information or reject values that cannot meet the contract.

Check. Selected Clippy floating-point/cast checks; boundary and round-trip tests; numerical review. Candidate CodeQL checks can locate values reaching sensitive conversion APIs.

Sources, level and coverage limits

Scope: Floating-point calculations, conversions and persistence.

Origin: S-CORE interpretation of MISRA C++:2023 guidelines.

MISRA C++:2023 sources (draft SCRC assessment): 0.3.1 (SCRC draft: safe).

Adaptation notes: Adapts Directive 0.3.1; the shared-contract permission is an S-CORE choice.

Level rationale: Required although Directive 0.3.1 is Advisory: unspecified floating-point range, precision or special-value handling produces silent numerical error in stored and compared values, which is a safety consequence rather than a style concern.

Coverage limit: A lint cannot select application tolerances or prove numerical accuracy. Components that store integers as f64 (for example in a JSON backend) need an explicit round-trip contract.

SCR-RUST-006: Validate preconditions at trust boundaries#

Rule (Required). Only call a function when its documented preconditions hold; validate untrusted and stored input first and return an error otherwise.

Why it matters in Rust. The type system cannot express every precondition. A safe function that reads out of range on an unexpected input is still a defect, and a safe wrapper around unsafe that trusts its caller can make the whole program unsound.

Requirement. A function shall be called only when its documented preconditions hold. Encode invariants in validated types where possible; otherwise validate untrusted values before use and return a defined error. Stored data shall be treated as potentially malformed.

Example.

// Compliant for this input contract: an untrusted rate is valid only in 1..=10.
fn rate(raw: u8) -> Result<u8, ()> {
    if (1..=10).contains(&raw) { Ok(raw) } else { Err(()) }
}

// Non-compliant: accepts out-of-range input.
fn rate(raw: u8) -> Result<u8, ()> {
    Ok(raw)
}

Both compile. Only the first rejects input outside the documented precondition.

Check. Type/API review and negative tests; candidate CodeQL source-to-use checks with explicitly modeled validators and error paths.

Sources, level and coverage limits

Scope: Public APIs, external data, stored data and unsafe wrappers.

Origin: S-CORE interpretation of MISRA C++:2023 guidelines.

MISRA C++:2023 sources (draft SCRC assessment): 0.3.2 (SCRC draft: safe).

Coverage limit: A validation call is not sufficient evidence unless the checked property and success branch match the precondition. Arbitrary application contracts require review.

SCR-RUST-007: Isolate unsafe operations and establish their contracts#

Rule (Required). Keep unsafe in identified modules, document the invariant each unsafe operation relies on, and make sure every safe wrapper is sound for every input its signature allows.

Why it matters in Rust. unsafe turns off the compiler’s guarantees for that block. Undefined behaviour is not a crash you can catch; it can corrupt data silently anywhere in the program. A safe API that is unsound makes every caller unsafe without them knowing.

Requirement. Undefined behavior is prohibited. Unsafe operations shall be confined to identified modules and justified by operation-specific invariants covering validity, lifetime, aliasing, alignment and concurrency as applicable. Safe APIs shall preserve soundness for all permitted safe callers. Crates designated safe-only shall forbid unsafe_code.

Example.

// Compliant: handles every slice length without unsafe access.
fn first(input: &[u8]) -> Option<u8> {
    input.first().copied()
}

// Non-compliant: the safe API permits an invalid read for input = &[].
fn first(input: &[u8]) -> Option<u8> {
    Some(unsafe { *input.as_ptr() })
}

Both function bodies compile. An empty slice is a valid input to either safe function; Miri accepts the first and reports undefined behavior for the second on an empty slice. A safe wrapper must be sound for every input its signature admits.

Check. rustc unsafe_op_in_unsafe_fn; Clippy missing_safety_doc and undocumented_unsafe_blocks; independent unsafe review; targeted Miri and applicable verification.

Sources, level and coverage limits

Scope: Unsafe code, unsafe traits/attributes, safe wrappers and their dependencies.

Origin: S-CORE interpretation of MISRA C++:2023 guidelines.

MISRA C++:2023 sources (draft SCRC assessment): 4.1.3 (SCRC draft: safe).

Coverage limit: Documentation checks establish presence, not correctness. Miri covers supported executed paths. A crate with no unsafe blocks may still rely on unsafe dependencies; panic freedom is a separate property.

SCR-RUST-008: Control shared state and memory ordering#

Rule (Required). Give every piece of shared mutable state an owner, an initialization protocol and a synchronization design. Do not use static mut in production code.

Why it matters in Rust. Rust prevents data races in safe code, but not deadlocks, lock-order inversions, wrong atomic orderings or logically racy protocols. A static without mut can still be mutated through a Mutex or an atomic, and static mut has no protection at all.

Requirement. Shared mutable state shall have a documented owner, initialization protocol and synchronization design. The rule covers every item reachable from more than one thread, or from more than one function through a shared path, including static items without mut whose type provides interior mutability (Mutex, RwLock, atomics, OnceLock, UnsafeCell) and thread_local! storage. const items, static items of types without interior mutability, and locals that never escape their function are excluded. static mut is prohibited in first-party production code. A reviewed exception requires single-writer or externally synchronized access documented at the declaration, no references to the item, and raw-pointer access confined to the owning module. Each use of shared globals, atomics and unsafe Send/Sync shall justify ordering and lifecycle assumptions. Lock ordering and reentrancy constraints shall be documented.

Check. Compiler trait checks; rustc static_mut_refs (deny by default in edition 2024) for references to mutable statics; a syntax check for static mut declarations; shared-state inventory, unsafe review and concurrency tests; candidate checks for global-state access and unsafe trait implementations.

Sources, level and coverage limits

Scope: All shared state, including Mutex, atomics and unsafe implementations.

Origin: S-CORE interpretation of MISRA C++:2023 guidelines.

MISRA C++:2023 sources (draft SCRC assessment): 6.7.1 (SCRC draft: safe), 6.7.2 (SCRC draft: safe).

Adaptation notes: Adapts 6.7.1 and 6.7.2. The C++ exclusions for const/constexpr objects correspond to const items and static items without interior mutability; a static holding a Mutex or atomic is in scope. The first-party static mut ban with reviewed exceptions is the S-CORE policy choice.

Coverage limit: Safe Rust prevents many data races under soundness assumptions but does not prevent deadlocks, logical races or incorrect atomic protocols. static_mut_refs catches references, not declarations or raw-pointer uses; the declaration ban needs its own check.

SCR-RUST-009: Remove disabled code from comments#

Rule (Advisory). Delete obsolete code instead of parking it in comments or behind a permanently false cfg; let version control remember it.

Why it matters in Rust. Commented-out code rots, misleads readers and cannot be checked by the compiler. Rust nests block comments, so a stray /* can hide a whole section. A #[cfg(any())] block is the same thing with different syntax.

Requirement. Obsolete implementations shall be removed and recovered through version control when needed, rather than parked in comments or behind permanently false or undeclared cfg predicates. Supported feature, target and test configurations are intentional conditional compilation and are not affected. Nested block comments shall not be used to disable code, since Rust nests /* */ and a stray delimiter can hide a whole section; a block comment containing code shall be a documentation example or explanatory pseudocode. Comments should explain intent and constraints.

Check. Code review; a comment-pattern checker may identify candidates; rustc unexpected_cfgs with check-cfg identifies undeclared predicates used to park code.

Sources, level and coverage limits

Scope: Production source comments.

Origin: S-CORE interpretation of MISRA C++:2023 guidelines.

MISRA C++:2023 sources (draft SCRC assessment): 5.7.1 (SCRC draft: safe), 5.7.2 (SCRC draft: safe).

Adaptation notes: Adapts 5.7.2 (commented-out code) with permanently false cfg predicates as the Rust analogue of #if 0, and the nested block comment concern of 5.7.1.

Level rationale: Advisory although Rule 5.7.1 is Required: text matching cannot reliably separate disabled code from documentation, so enforcement rests on review judgement. The nested block comment hazard from 5.7.1 is recorded in the requirement.

Coverage limit: Text matching cannot reliably distinguish obsolete code from useful documentation.

SCR-RUST-010: Make array and buffer extents explicit at interfaces#

Rule (Required). Pass arrays and slices, which carry their length, in Rust interfaces; where a raw pointer and length must be used, document and validate them together before building a slice.

Why it matters in Rust. A slice is always in bounds. A raw pointer with a separate length is only as valid as the caller promises, and constructing a slice from a wrong pair is undefined behaviour even before the first access.

Requirement. Use arrays or slices that carry the required extent in native Rust interfaces. Raw buffer interfaces shall document pointer, length, ownership and validity together, with validation before constructing a slice.

Check. Compiler typing for native arrays/slices; API review and boundary tests for raw pointer/length pairs.

Sources, level and coverage limits

Scope: Rust APIs and foreign buffer boundaries.

Origin: S-CORE supplement (raw buffer extents at foreign interfaces).

MISRA C++:2023 sources (draft SCRC assessment): No MISRA C++ source retained.

Coverage limit: Native array extents are largely compiler-enforced. FFI buffer validity is not, and bounds-checked access can still panic.

SCR-RUST-011: Keep imports and module interfaces explicit#

Rule (Advisory). Make imports and re-exports show where each name comes from, keep glob imports to designated preludes, and make sure generated or included source can be traced to a reviewed input.

Why it matters in Rust. Readers and reviewers resolve names by eye. Glob imports and include! hide where an item is defined and can shadow items from an outer scope. Code that appears from a build script needs the same review as code that was typed.

Requirement. Imports and re-exports should make dependencies and ownership of names clear. Keep ordinary imports together; document exceptions for narrow local scope. Glob imports should be limited to explicitly designated preludes or tests. Generated or included source (include!, include_str!, build-script output, #[path] attributes) shall have controlled provenance: a reviewer can trace it to a reviewed source file or to a controlled build input recorded in the component’s source and build records, and generation is reproducible from those inputs. include! shall not shadow items of an outer scope.

Check. Formatting, compiler name resolution, selected import lints and review of re-export/prelude design.

Sources, level and coverage limits

Scope: Crate/module layout and source inclusion.

Origin: S-CORE interpretation of MISRA C++:2023 guidelines.

MISRA C++:2023 sources (draft SCRC assessment): 19.0.3 (SCRC draft: safe), 19.2.1 (SCRC draft: safe).

Adaptation notes: Adapts 19.0.3 and 19.2.1 (include! shadowing outer items). Provenance evidence is satisfied by existing source and build records.

Level rationale: Advisory although Rule 19.2.1 is Required: Rust’s module system removes the undefined and ambiguous behavior of C++ header inclusion, leaving clarity and provenance of names as the residual concern.

Coverage limit: Rust permits include! and generated source; valid syntax alone does not establish clarity or provenance.

SCR-RUST-012: Reserve entry-point naming#

Rule (Required). Use the name main only for real executable entry points.

Why it matters in Rust. A nested function called main is legal Rust but misleads anyone searching for the program’s entry point. This is a project naming convention, not a language rule.

Requirement. Reserve main for actual executable entry points. Other production functions shall use names expressing their role. Generated wrappers and embedded entry-point conventions require an explicit scoped exception.

Example.

// Compliant: the helper's name describes its role.
mod worker {
    pub fn process() -> u8 { 1 }
}
fn main() { let _ = worker::process(); }

// Non-compliant: worker::main is not an executable entry point.
mod worker {
    pub fn main() -> u8 { 1 }
}
fn main() { let _ = worker::main(); }

Both compile and run. The nested main violates the naming policy; worker is an ordinary production module with no generated-wrapper or embedded-entry-point exception.

Check. A syntax/name checker can enforce the declared policy; review generated and platform entry points.

Sources, level and coverage limits

Scope: First-party production functions.

Origin: S-CORE interpretation of MISRA C++:2023 guidelines.

MISRA C++:2023 sources (draft SCRC assessment): 6.0.4 (SCRC draft: safe).

Coverage limit: This is a project naming restriction, not a Rust language requirement.

SCR-RUST-013: Control exported symbols and foreign declarations#

Rule (Required). Exported symbols need unique names and compatible declarations in each binary; keep foreign declarations in reviewed binding modules and justify every linkage attribute.

Why it matters in Rust. #[no_mangle] and export_name put an item into the global symbol namespace shared with C. A duplicate or mismatched declaration is not caught by Rust’s name resolution; the linker, or the running program, finds it.

Requirement. Exported symbols shall have unique definitions and compatible declarations in each delivered binary. Centralize foreign declarations in reviewed binding modules or crates; an extern declaration shall be type-compatible with the foreign definition. Use minimal visibility and justify no_mangle, export_name, link_section and equivalent linkage controls. Items exported with #[no_mangle], #[unsafe(no_mangle)] or export_name enter the global symbol namespace: each shall be declared in a reviewed binding module and its name shall be unique across the delivered binary.

Check. Compiler/linker checks, binding review and final symbol-table inspection for each delivered target.

Sources, level and coverage limits

Scope: Linkage attributes, exported symbols and foreign bindings.

Origin: S-CORE interpretation of MISRA C++:2023 guidelines.

MISRA C++:2023 sources (draft SCRC assessment): 6.0.3 (SCRC draft: unsafe), 6.2.1 (SCRC draft: unsafe), 6.2.2 (SCRC draft: unsafe).

Adaptation notes: Adapts 6.0.3 (no_mangle items in the global namespace), 6.2.1 and 6.2.2 (extern declarations compatible with the C definition).

Coverage limit: Cross-crate/linker behavior is not fully captured by Rust name resolution. Edition 2021 permits syntax that edition 2024 marks unsafe; do not scope this check by unsafe blocks alone.

SCR-RUST-014: Avoid misleading name shadowing and method resolution#

Rule (Required). Do not rebind a name to a value that means something different. A same-name rebinding is fine when it is the same quantity, refined; use explicit paths when inherent and trait methods collide.

Why it matters in Rust. let input = input.trim(); is idiomatic and clear. let timeout = timeout * 1000; silently changes the unit under the same name, and later uses cannot tell which unit they get. Method resolution preferring inherent methods can likewise pick a different function than the reader expects.

Requirement. Rebinding shall not silently change the logical meaning of a value. A same-name binding is permitted when the new value is the same quantity in a refined form (trimmed, parsed, validated, unwrapped) and the transformation is visible in the initializer. It is prohibited when the new binding represents a different quantity, unit or role. Where inherent and trait methods share a name but differ semantically, use explicit qualification or change the API.

Example.

// Compliant: same quantity, refined form, transformation visible.
fn parse(input: &str) -> Option<u32> {
    let input = input.trim();
    input.parse().ok()
}

// Non-compliant: the same name now holds a different unit.
fn schedule(timeout: u32) -> u32 {
    let timeout = timeout * 1000; // seconds silently become milliseconds
    timeout + 1
}

Both compile. In the first the rebinding is still input, only trimmed. In the second timeout changes unit under the same name, so later readers cannot tell which unit a use refers to.

Check. Selected Clippy shadowing checks plus type-aware custom checks and review of trait/inherent method collisions.

Sources, level and coverage limits

Scope: Bindings, inherent methods and trait methods.

Origin: S-CORE interpretation of MISRA C++:2023 guidelines.

MISRA C++:2023 sources (draft SCRC assessment): 6.4.1 (SCRC draft: safe).

Adaptation notes: Adapts 6.4.1. The inherent-versus-trait method resolution policy is an S-CORE addition: the SCRC draft assesses 6.4.2 as not applicable until supertrait_item_shadowing stabilizes.

Coverage limit: This intentionally adapts the C++ restriction to Rust idioms. Rust trait composition is not class inheritance; a broad shadowing ban would enforce a different policy. Clippy shadow lints cannot judge whether a quantity changed meaning.

SCR-RUST-015: Preserve lifetimes across raw interfaces#

Rule (Required). Never access memory after its referent has gone, and do not hand out raw pointers to locals or capture them in callbacks that may outlive the data.

Why it matters in Rust. The borrow checker protects references, not raw pointers. Creating, storing or passing a dangling raw pointer compiles; the undefined behaviour happens at the later access, often far from where the pointer was made.

Requirement. An access shall not outlive its referent. Do not expose a dangling local pointer as a usable API result or store borrowed addresses beyond their valid lifetime. A closure or callback that captures a raw pointer shall be invoked only while the pointee is live.     // SAFETY: q is back at the initialized first byte; bytes is still live.
    unsafe { *q }
}

// Non-compliant: add(20) itself exceeds its permitted bounds.
fn read_first() -> u8 {
    let bytes = [1_u8, 2];
    let p = bytes.as_ptr();
    let q = unsafe { p.add(20) }.wrapping_sub(20);
    unsafe { *q }
}

Origin: S-CORE interpretation of MISRA C++:2023 guidelines.

MISRA C++:2023 sources (draft SCRC assessment): 14.1.1 (SCRC draft: safe).

Level rationale: Required although Rule 14.1.1 is Advisory: visibility is the only language mechanism that protects a type invariant in Rust; a public field lets safe code create an invalid state without any diagnostic.

SCR-RUST-035: Review ownership traits and resource lifecycle#

Rule (Required). Implement Copy, Clone and Drop so they preserve ownership and invariants, give every resource a release policy, keep guards alive for their intended duration, and be explicit when converting borrowed data to owned.

Why it matters in Rust. Rust does not guarantee destructors run: mem::forget, leaks and aborts skip them. A let _ = mutex.lock() releases the lock immediately. A generic .into() may move or copy depending on the argument type, and the reader cannot tell which.

Requirement. Copy, Clone and Drop implementations shall preserve ownership and type invariants. Every acquired resource shall have a defined release or transfer policy, including partial failure paths. Unsafe pinning abstractions shall preserve their promised pinning invariants. Do not rely on destructors running to maintain memory safety. Synchronization and resource guards shall remain bound for the intended duration; do not accidentally discard them immediately. Where a borrowed-to-owned conversion matters, use an explicit operation such as to_vec(), to_owned() or clone() rather than a generic From/Into call whose behavior, moving an owner or copying from a borrow, depends on the argument type. APIs that emulate move or assignment through raw pointers, including Pin-based move emulation and in-place replacement, shall define behavior when source and destination coincide: either the aliasing case preserves the value, invariants and resources, or it is an explicit unsafe precondition that every safe wrapper establishes.

Check. Compiler move/trait checks, review of custom implementations and targeted Miri/resource-failure tests; inventory mem::forget, leaks and manual ownership transfer. Include the rustc let_underscore_lock diagnostic where supported.

Sources, level and coverage limits

Scope: Copy/Clone/Drop, pinning, custom owners and raw allocation wrappers.

Origin: S-CORE interpretation of MISRA C++:2023 guidelines.

MISRA C++:2023 sources (draft SCRC assessment): 15.0.1 (SCRC draft: safe), 15.8.1 (SCRC draft: unsafe), 21.6.2 (SCRC draft: safe), 28.6.1 (SCRC draft: safe).

Adaptation notes: Adapts 15.0.1, 21.6.2, 28.6.1 (explicit borrowed-to-owned conversion) and Directive 15.8.1 (self-aliasing in move emulation).

Coverage limit: Safe Rust permits leaks and mem::forget, and termination may skip Drop. Pin is a type, not a trait. The compiler decides whether a generic conversion moves or copies, but a reader cannot see which without an explicit operation.

SCR-RUST-036: Define panic, termination and cleanup behavior#

Rule (Required). Handle recoverable failures with Result, never terminate the process from a library, keep destructors panic-free, and decide per boundary whether a path must be panic-free or only panic-contained.

Why it matters in Rust. A panic is not an error you can always catch: under panic=abort it ends the process, a panic during unwinding aborts, and indexing, arithmetic and allocation panic implicitly. std::process::exit skips every destructor. Whether a wrapper may catch and convert a panic is a design decision that has to be made explicitly.

Requirement. Recoverable failures shall use explicit error handling. Application libraries shall not terminate the process directly or indirectly: calling std::process::exit or abort, taking or storing their addresses, or reaching them through foreign code is prohibited. The only accepted fail-stop is the abort produced by a failed assertion or by the delivered panic strategy; any broader fail-stop path requires a documented system response including cleanup or external recovery. Each boundary declares one of two levels: a panic-free path never initiates a panic, including implicit panics from indexing, arithmetic and allocation; a panic-contained boundary may see a panic but shall not let it escape. Destructors are panic-free: a custom Drop and the field cleanup it relies on shall not panic. No panic shall cross a foreign-language boundary. Panic payloads shall carry only owned data or 'static references. The conditions for catch_unwind, the panic strategy and payload contents are specified in Panic boundaries.

Check. Selected Clippy panic/unwrap_used/expect_used restrictions; clippy::exit for direct calls plus an inventory of stored or passed function pointers to termination APIs; failure-injection tests and call-path review; Miri or tests for destructor panic paths.

Sources, level and coverage limits

Scope: Production library code, process boundaries and destructors.

Origin: S-CORE interpretation of MISRA C++:2023 guidelines.

MISRA C++:2023 sources (draft SCRC assessment): 18.1.1 (SCRC draft: unsafe), 18.4.1 (SCRC draft: safe), 18.5.1 (SCRC draft: safe), 18.5.2 (SCRC draft: safe).

Adaptation notes: Adapts 18.1.1 (payloads; permitting 'static references is a Rust adaptation of the C++ pointer restriction), 18.4.1 (destructor panics), 18.5.1 (unwinding across boundaries) and 18.5.2 (termination, including indirect calls; the only accepted fail-stop is the assertion or panic-strategy abort).

Coverage limit: Absence of panic! and unwrap does not prove panic freedom: indexing, arithmetic, dependencies and destructors can fail. clippy::exit sees direct calls only. Panic is not synonymous with Rust undefined behavior; the system may nevertheless treat it as a safety failure.

SCR-RUST-037: Validate attributes and configuration coverage#

Rule (Required). Declare every cfg name and feature value and have the compiler check them; analyze every supported configuration, not just one all-features build.

Why it matters in Rust. A misspelled #[cfg(feature = "enabeld")] silently removes the code it guards. Inactive code is not type-checked, so a bug behind the wrong flag only appears when that configuration ships.

Requirement. All cfg names/values and features shall be declared and checked. Invalid or unrecognized attributes/configuration diagnostics shall block analysis. Maintain and analyze the supported configuration matrix, including mutually exclusive features, rather than assuming one all-features build is representative.

Example.

// Compliant feature spelling.
#[cfg(feature = "enabled")]
fn feature_marker() {}
fn main() {}

// Non-compliant: undeclared, misspelled feature value.
#[cfg(feature = "enabeld")]
fn feature_marker() {}
fn main() {}

With the only declared feature value being enabled and --check-cfg 'cfg(feature, values("enabled"))' -D unexpected_cfgs, the first passes and the second is rejected by the unexpected_cfgs lint even though the feature is inactive. See the rustc check-cfg documentation.

Check. rustc unexpected_cfgs and appropriate check-cfg flags, attribute diagnostics, build-matrix checks and configuration review.

Sources, level and coverage limits

Scope: cfg/features, attributes and build-generated configuration.

Origin: S-CORE interpretation of MISRA C++:2023 guidelines.

MISRA C++:2023 sources (draft SCRC assessment): 19.0.1 (SCRC draft: not applicable, retained by S-CORE).

Coverage limit: Inactive code is not necessarily type-checked. Correct configuration syntax does not establish that every delivered variant was analyzed.

SCR-RUST-038: Control macro expansion and argument effects#

Rule (Required). Prefer a function to a macro unless the macro is needed for variadic arity, item generation, compile-time processing or caller location, and document how often a macro evaluates its arguments.

Why it matters in Rust. Macros duplicate or skip the evaluation of their arguments without any warning, and the code they generate escapes ordinary review. A function has a signature the compiler and the reader can check.

Requirement. Prefer a function where a function can express the intended behavior. A macro is justified for variadic arity, item or implementation generation, compile-time token or string processing, or capturing the caller location, and the crate shall state which of these exceptions it uses. Macros shall document whether arguments are evaluated once, more than once or not at all. Use expression fragments where expression semantics are intended. Safety-relevant macro-generated unsafe code and effects shall be included in review and checker coverage.

Check. Macro expansion inspection, tests using arguments with observable effects, and lint coverage checks on generated code.

Sources, level and coverage limits

Scope: Declarative/procedural macros and generated Rust.

Origin: S-CORE interpretation of MISRA C++:2023 guidelines.

MISRA C++:2023 sources (draft SCRC assessment): 19.0.2 (SCRC draft: safe), 19.3.4 (SCRC draft: safe).

Adaptation notes: Adapts 19.0.2 (functions preferred over function-like macros, with stated exceptions) and 19.3.4.

Coverage limit: Rust macros avoid some C++ textual-substitution hazards but can still duplicate evaluation, introduce panics or unsafe code. Compiler type checking is not a substitute for semantic review.

SCR-RUST-039: Bound allocation and isolate manual allocators#

Rule (Required). Say where allocation is allowed, bound input-driven growth, and keep custom allocators and raw allocation APIs in reviewed modules.

Why it matters in Rust. An attacker-controlled length that reaches Vec::with_capacity is a denial of service. Allocation failure aborts by default; try_reserve covers only some cases. RAII frees memory but does not bound how much you hold.

Requirement. Each component shall declare where allocation is permitted and justify peak memory, growth limits and failure behavior. Unbounded input-driven growth is prohibited. Manual allocators and raw allocation APIs shall be restricted to reviewed modules with allocator/layout/ownership contracts.

Check. Allocation API inventory, workload/boundary/failure tests and memory-budget review; candidate CodeQL flow checks for untrusted size inputs.

Sources, level and coverage limits

Scope: Heap allocation, container growth and custom allocation.

Origin: S-CORE interpretation of MISRA C++:2023 guidelines.

MISRA C++:2023 sources (draft SCRC assessment): 21.6.1 (SCRC draft: safe), 21.6.3 (SCRC draft: unsafe).

Adaptation notes: Adapts 21.6.1 and 21.6.3; 21.6.4 is assessed not applicable because GlobalAlloc::dealloc always receives the layout.

Coverage limit: A blanket no-allocation profile is an optional stricter component policy, not silently imposed here. try_reserve covers only particular failures; RAII does not bound memory, prevent leaks or guarantee recovery from OOM.

SCR-RUST-040: Separate compile-time and runtime assertions#

Rule (Required). Check compile-time invariants with const evaluation; keep required runtime checks active in release builds and never put needed logic inside debug_assert!.

Why it matters in Rust. debug_assert! disappears when debug assertions are off, which is the normal release setting. A check that only exists in test builds is not a check.

Requirement. An invariant intended for compile-time checking shall use a const-evaluated construct supported by the pinned compiler. Required runtime validation shall remain active in production and return the specified error or enter the approved failure path. Do not put required side effects inside debug_assert!.

Example.

// Compliant: the check remains active in production.
fn check(value: u8) -> Result<(), ()> {
    if value <= 10 { Ok(()) } else { Err(()) }
}

// Non-compliant: the required check can disappear.
fn check(value: u8) -> Result<(), ()> {
    debug_assert!(value <= 10);
    Ok(())
}

Both compile. The API must reject values above 10 in production builds too; with -C debug-assertions=no the second returns Ok(()) for 11. debug_assert! is conditional on that build setting and cannot carry a required runtime check.

Check. Compiler const evaluation; Clippy assertions_on_constants as a candidate; release-configuration tests and assertion review.

MISRA C++:2023 sources (draft SCRC assessment): 22.3.1 (SCRC draft: safe).

SCR-RUST-041: Account for dependency and generated-code soundness#

Rule (Required). Keep an inventory of dependencies and code generators, record the evidence relied on for their unsafe code and features, and state clearly that a crate’s safe-only status covers first-party code only.

Why it matters in Rust. #![forbid(unsafe_code)] says nothing about the crates you link. Your soundness depends on every unsafe block in every dependency and every generated file.

Requirement. Maintain the dependency/generator inventory and record the evidence relied on for unsafe implementations, feature selection and foreign code. Component safe-only status shall describe first-party source scope separately from the full linked dependency graph.

Check. Dependency lock/configuration review, unsafe/binding inventories, change-impact review and relevant integration tests.

SCR-RUST-042: Assess foreign-language boundaries explicitly#

Rule (Required). Make every Rust/C boundary explicit: matching ABI and layout, documented ownership and lifetimes, no panic or exception crossing the boundary, and the C library’s own rules for errno, locale, signals and returned storage.

Why it matters in Rust. FFI is where both languages’ guarantees stop. A panic reaching an extern "C" frame aborts, a C++ exception entering Rust is undefined behaviour, and a pointer returned by getenv or localtime can be invalidated by the next call on another thread.

Requirement. Foreign bindings shall match the actual ABI, layout, types and exported definitions. Document ownership, pointer and length contracts, threading and callback lifetime, error conventions and unwinding behavior in both directions. No Rust panic shall reach a foreign frame and no foreign exception shall enter Rust. setjmp/longjmp and similar nonlocal transfers shall not cross a Rust frame. Signal handling, errno and error-state handling, the process-wide locale, and storage returned by C library functions shall follow the contracts in Foreign-language boundaries. Assess C and C++ implementations under their own applicable policy.

Check. Binding, layout and symbol review and tests on delivered targets; MISRA C:2025 Addendum 6 cross-check, whose comments on R.8.3, R.8.5, R.8.6 and R.8.15 provide boundary cross-references; review of each contract on the boundary contracts page.

SCR-RUST-043: Record coverage, deviations and residual obligations#

Rule (Required). For every adopted rule, record how it is checked, which checker version and configuration, what the checker misses, and every deviation with its owner.

Why it matters in Rust. A clean lint run is only evidence for the cases the lint sees. Without a record of coverage and blind spots, nobody can tell a verified rule from an unchecked one.

Requirement. Each required adopted rule shall have evidence of conformance or an approved scoped deviation. Record rule version, configuration, checker version, known blind spots and review/test evidence. Advisory nonconformances shall be considered and dispositioned. Safety-relevant liveness, timing and persistence guarantees need separate requirements and verification.

Check. Rule-to-checker coverage register, deviation validation and release evidence review. Separate test/tooling profiles shall not suppress production library obligations.
