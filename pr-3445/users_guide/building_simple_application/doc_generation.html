Documentation generation#

Introduction#

As described in the Overview of technologies chapter, Eclipse S-CORE uses the Sphinx and sphinx-needs toolchain to generate documentation from rst files. Elements of the Eclipse S-CORE metamodel, e.g. requirements, architecture elements and test cases, are represented as sphinx-needs objects.

The integration of Sphinx, sphinx-needs, and the Eclipse S-CORE-specific extensions is implemented in the repository:

  • eclipse-score/docs-as-code

The docs-as-code how-to documentation describes in detail how documentation is created and built. Here, we focus on a simple example.

Defining a Bazel Documentation Target#

To generate HTML documentation from .rst files, S-CORE provides the docs Bazel macro. In the top-level BUILD file of your module, you find a call of this macro. Without the bundles explained below, it looks like this:

1load("@score_docs_as_code//:docs.bzl", "docs")
2
3docs(
4    project = "Module Template Project",
5    project_url = "https://eclipse-score.github.io/module_template/",
6    source_dir = "docs",
7)

The most important parameters are:

  • source_dir: the directory that is given to Sphinx as source directory. Sphinx does not rely on Bazel dependencies to decide which files are included, but on its own toctree mechanism, starting from index.rst.

  • project and project_url: the name and the published URL of your documentation. With both set, no own conf.py is needed; all S-CORE Sphinx extensions and the metamodel checks are configured by docs-as-code. Replace the template values by the name and URL of your module.

  • external_needs: documentation of other modules whose sphinx-needs objects you want to reference, e.g. "@score_process_description//:docs" for the process description or "@score_platform//:docs" for the feature requirements and architecture of the S-CORE platform. The module must also be declared with bazel_dep in MODULE.bazel. See Reference Other Modules for details.

  • bundles: further documentation bundles which are mounted into your documentation, e.g. the documentation of each component in score/<component_name>. The template mounts //score/component_example:docs and //examples:docs this way.

The index.rst file in source_dir is the main entry point for your documentation. It includes all other rst files that should be part of the documentation build.

Building documentation#

The docs macro creates the following targets:

Command

Purpose

bazel run //:docs

Builds the HTML documentation into the _build folder

bazel run //:docs_check

Checks the documentation, incl. the metamodel and traceability checks, without creating HTML

bazel run //:docs_link_check

Checks all external links

bazel run //:live_preview

Starts a local server which rebuilds the documentation on every change

bazel run //:ide_support

Creates the virtual environment .venv_docs for IDE support (e.g. the Esbonio extension)

The first execution of a Bazel command may take longer, because Bazel needs to download toolchains and dependencies. Subsequent runs will be much faster.

$ bazel run //:docs
...
reading sources... [100%] index
...
Needs successfully exported
build succeeded.

The HTML pages are in _build.

After a successful build, open _build/index.html in a web browser.

When working on the documentation, it is helpful to see the current status directly in the web browser. Use the live preview for this:

$ bazel run //:live_preview
...
build succeeded.

[sphinx-autobuild] Serving on http://127.0.0.1:8000
[sphinx-autobuild] Waiting to detect changes...

A local server is started on http://127.0.0.1:8000. Open it in your web browser to view the current version of the documentation. The live preview:

  • rebuilds automatically

  • updates on every file change

  • stays active until you stop the Bazel process (Ctrl+C).

The published documentation of the module template shows what the result looks like.

Linking tests to requirements#

The documentation does not only contain the rst files: docs-as-code also reads the results of the Bazel tests and links each test case to the requirements it verifies. This is how the traceability from requirements to tests becomes visible in the generated documentation.

The platform integration test of the running example shows how this works. The test function is annotated with the requirement it verifies and the applied test methods (test_platform_info_showcase.py):

 1from attribute_plugin import add_test_properties
 2
 3@add_test_properties(
 4    partially_verifies=["stkh_req__communication__inter_process"],
 5    test_type="interface-test",
 6    derivation_technique="requirements-analysis",
 7)
 8def test_platform_version(target):
 9    output = run_showcases(target, "Platform Version Check")
10    assert "platform_info_consumer: S-CORE version check passed" in output

The attribute plugin writes these properties into the JUnit XML result of the test. During the documentation build, they become a test case need which is linked to the stakeholder requirement stkh_req__communication__inter_process. The allowed requirement types depend on the test level, see the software verification plan.
