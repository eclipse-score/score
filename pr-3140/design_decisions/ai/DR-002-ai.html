DR-010-Infra: AI SDLC Tooling Evaluation and S-CORE Harness Direction#

  • Issue: #3115 — Evaluate AI SDLC / SpecKit Tooling

  • Date: 2026-07-31 (rev. 2)

AI SDLC Tooling Evaluation and S-CORE Harness Direction
status: proposed
context: Infrastructure
decision: Build a thin, S-CORE-owned layer of reference agents/skills and MCP automation that drives the existing S-CORE process and Sphinx-Needs traceability, operating entirely within the current process metamodel and its established artifact types. Reuse concepts from SpecKit, Syspilot and Pharaoh rather than adopting any framework wholesale. Tool qualification and operational rollout are handled separately.
version: 2
dec_rec__infra__ai_sdlc_tooling
Decision Record

1. Context and Problem Statement#

S-CORE already has a complete development and design process, with its associated artifacts defined in the process model, Sphinx-Needs traceability as the artifact backbone, and governance enforced through contribution rules, code owners and CI. This record builds on that process; it does not replace it.

The gap this record addresses is narrower: S-CORE has no defined, governed way for AI agents to participate in that process while preserving its traceability and reviewability. The decision to make is:

Should S-CORE adopt one external AI-SDLC framework, depend on several, or build and own a thin automation layer that drives the existing process?

This is a tooling/integration decision, not a process-definition decision.

2. Scope and Non-Goals#

In scope

  • Decide the evaluation outcome and the prototyping direction for AI-SDLC tooling.

Explicit non-goals

  • This record keeps any harness outside the S-CORE toolchain used to produce release artifacts, pending a separate qualification decision.

  • This record makes no ASIL-B / tool-qualification claim. Qualification (confidence in the use of software tools, ISO 26262-8) is a separate, later decision and a precondition before any such tooling could touch qualified work products.

  • The automation layer works entirely within the existing process metamodel and its established artifact (need) types, keeping that model authoritative and unchanged. Agents consume it and extend its coverage, not its definition.

  • Operational rollout, enforcement, and agent granularity are tracked as follow-ups (Section 11).

    Rationale: several reviewers correctly noted that making AI tooling part of the toolchain raises a qualification question that must be answered with a clear “yes” before adoption. This record is deliberately scoped below that line so the evaluation can land without pre-empting qualification.

3. Evaluation Method and Evidence Basis#

The evaluation draws on three distinct, separately-labelled evidence sources, so reviewers can weigh each appropriately:

  1. Desk scan (repository evidence). Each framework was assessed against ten categories from its own source repository (agents/skills, schemas, templates, license, configuration) — Section 4 and Section 12. This is a structured comparison, not a claim of hands-on operation on the S-CORE codebase.

  2. Field evidence. Hands-on PoC findings contributed during review — notably on OpenSpec and BMAD — are incorporated where they sharpen the desk scan (see Section 4.5 and the loopback finding in 8.3).

  3. Prototype evidence. The direction in Section 7 is grounded in the in-flight S-CORE prototype in eclipse-score/mcp-servers (metamodel-flow), which is hands-on experience on S-CORE’s own model rather than a third-party demo.

Scoring scale: 1 Poor · 2 Limited · 3 Acceptable · 4 Strong · 5 Excellent. Evaluation prioritized enterprise-scale collaborative engineering and compliance evidence over individual developer productivity.

4. Tool-by-Tool Analysis#

4.1 Syspilot#

Built directly on Sphinx-Needs; agents follow deterministic requirement links (“the map, not the flashlight”), with change-impact producing focused context (O(affected), not O(total)).

  • Strengths: native Sphinx-Needs orientation; strong traceability mindset; manager/engineer agent roles across the lifecycle.

  • Weaknesses: README labels it an early research project; hard dependency on VS Code, Copilot and enthali.jarvis-core; governance not enterprise-hardened.

  • S-CORE view: valuable source of concepts for the traceability layer.

4.2 BMAD Method#

Broad AI-assisted agile framework (34+ workflows, role agents); about collaboration patterns rather than regulated engineering evidence.

  • Strengths: mature packaging (npm v6.10.0, MIT), CI-friendly tooling.

  • Weaknesses: not Sphinx-Needs or ASPICE native; traceability is not the central artifact model.

  • S-CORE view: best kept for ideation/facilitation; not compliance evidence.

4.3 SpecKit#

Strongest specification-first workflow: constitution → specify → plan → tasks → analyze → implement, with CLI, templates and phase gates.

  • Strengths: specs as versioned artifacts; governance primitives; broad agent support (30+); MIT.

  • Weaknesses: not built for Sphinx-Needs, Bazel, ADRs or ASPICE; traceability is workflow-level; requirement IDs, Needs links and test evidence require S-CORE-specific integration.

  • S-CORE view: best reused as a phase shell (Section 8) whose outputs are S-CORE needs.

4.4 Pharaoh#

Conceptually the closest match: Sphinx-Needs V-model skill chain with explicit ASPICE 4.0 / ISO 26262-8 / ISO 21434 conformance concepts, enforcing mode, review metadata and reproducibility checks.

  • Weaknesses: repository archived (read-only since 2026-07-28); skills moved to commercial-adjacent ubCode/ubTrace; “AI is the runtime” is hard to certify/stabilize.

  • S-CORE view: best reference design; reuse concepts rather than depend on the archived repo.

Note

Verified: useblocks/pharaoh-skills is archived (read-only) as of 2026-07-28 (latest release v1.2.1). Functionality is stated to have moved into ubCode / ubTrace.

4.5 OpenSpec#

Added following review feedback; assessed primarily from field PoC (a concurrent-development evaluation) rather than desk scan.

  • Strengths: simple, lightweight SDD workflow; maintained; low adoption cost.

  • Weaknesses (field-observed): not Sphinx-Needs or ASPICE native; no loopbacks within an ongoing change — once tasks are derived, agents implement and iterate but are never returned to re-check that implementation still matches the original specification, or to raise requirements discovered late (e.g. non-functional/test requirements). Holding even its own simple process requires constant supervision or supporting tooling.

  • S-CORE view: reinforces the core finding (Section 8.3): keeping S-CORE’s own process and artifact types authoritative — and driving them with automation — is more robust than replacing them with a tool’s defaults.

7. Decision#

Build and own a thin S-CORE layer — reference agents/skills plus MCP automation — that drives the existing S-CORE process and Sphinx-Needs traceability, reusing proven concepts rather than adopting any framework wholesale.

  • Reuses the existing model as-is. Agents read the current process metamodel and its defined artifact (need) types via the cached sidecar graph (metamodel-flow, process_graph.json), keeping it the single source of truth.

  • SpecKit — adapt as a phase shell. Reuse its phase structure; every output is an existing S-CORE need.

  • Syspilot / Pharaoh — concepts. Requirement-driven traceability and change-impact (Syspilot); lifecycle governance and conformance (Pharaoh).

  • BMAD / OpenSpec — reference only. Useful for ideation; field evidence shows S-CORE’s own process is the more robust backbone to automate against.

8. Integration Architecture#

8.1 Principle#

The layer adds automation that drives the existing process. Every phase output is an existing S-CORE need, so the established artifact types remain the backbone and the generated chain stays native to S-CORE.

8.3 The loopback#

Field evaluation of SDD tools (OpenSpec, BMAD) found their decisive weakness: no loopback within an ongoing change. Agents implement and iterate but are never returned to confirm the implementation still matches the specification, or to raise requirements discovered late. The S-CORE layer makes this loopback a first-class, enforced gate (analyze → specify) rather than relying on a human to notice drift.

        flowchart LR
    A[Sphinx-Needs Requirements] --> B[specify]
    B --> C[plan: architecture / ADR]
    C --> D[tasks: detailed design]
    D --> E[implement: code + Bazel]
    E --> F[tests + evidence]
    F --> G[Sphinx documentation]
    G --> A
    F -->|loopback: drift detected| H{analyze: spec↔impl↔test aligned?}
    H -->|no| B
    H -->|yes| I[human sign-off]

9. Governance and Safety Principles#

  • One process step per agent. Agents are scoped narrowly and defer to skills, keeping context and review tractable.

  • Human sign-off at every gate. No artifact — requirement, design, code or test — enters the graph or merges without human approval.

  • Everything reviewable. Everything-as-code, including requirements and generated code, stays human-understandable and reviewable by the person signing it off.

  • Reproducible by construction. Prompts, templates, model settings, inputs and generated outputs are versioned in Git so every run is auditable and repeatable.

11. Open Questions / Follow-ups#

  • Qualification assessment — can this tooling meet ISO 26262-8 tool-use confidence before any toolchain role? (precondition, separate DR)

  • Agent granularity — e.g. a process-engineer agent deferring to per-step skills vs. role-specific agents. (separate design DR)

  • Relationship to mcp-servers metamodel-flow — this record sets the direction the prototype already pursues; keep the two in sync.

  • ubCode / ubTrace — reassess as the maintained Pharaoh successor.
